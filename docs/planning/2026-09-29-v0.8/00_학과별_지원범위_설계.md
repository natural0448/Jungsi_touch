# 대학을 먼저 보고, 학과별 지원 범위를 확인하는 화면 — v0.8

2026-09-29 사용자 요구 반영. 기존 v0.7과 원본 자료는 보존한다. 현재 산출물은 가상 데이터로 작동하는 화면과 서버 연동 계약이며, 실제 대학의 추천 판정이나 합격 예측을 완료한 것은 아니다.

## 확정한 요구와 화면 설계

사용자의 핵심 요구는 대학을 먼저 찾고, 그 대학에서 구체적으로 어떤 학과까지 지원을 검토할 수 있는지 클릭해서 보는 것이다. 같은 대학이라도 학과별 입결과 환산식이 달라 대학 분류를 모든 학과에 일괄 부여하지 않는다.

- `도전학교 / 핵심학교 / 여유 후보` 세 묶음 모두 동일한 학과 상세 기능을 제공한다. 사용자 문장의 ‘오전학교’는 문맥상 ‘도전학교’로 해석했다.
- 학교 묶음은 전체 성적 기반 1차 탐색의 맥락이다. 상세 추천은 학년도·실제 모집단위·전형·모집군마다 별도로 결정한다.
- 닫힌 대학 카드에서도 핵심 검토 학과와 여유 후보 학과의 이름, 도전·핵심·여유·확인 필요 개수를 보여준다.
- `학과별 지원 범위 보기`를 누르면 해당 대학에서 검토한 모집단위 전체가 펼쳐진다. 학과 추천 단계별 필터도 제공한다.
- 대학 카드의 단계별 개수 버튼을 누르면 그 단계에 해당하는 학과가 바로 펼쳐진다. ‘전체’로 돌아가 다른 학과도 볼 수 있다.
- 학과 행은 전형·모집군, 적용 반영식, 내 환산점수, 그 환산 기준의 내 상위 누적, 과거 합격권·상위70%, 올해 예상 기준, 추천 이유를 보여준다.
- 대학별 점수 만점이 다르므로 학교 간 환산점수 자체를 직접 비교·정렬하지 않는다. 같은 대학 내 복수 반영식도 학과마다 적용한다.
- `핵심학교`는 탐색 분류이고, `핵심 지원 학교`는 사용자가 학과를 선택해 만든 목록이다. 두 개념을 구분한다.
- 데스크톱 기본 학교 목록 2/3, 간호·보건·교육 와일드카드 1/3을 유지한다. 작은 화면에서는 순서대로 쌓는다.

학교당 1차 탐색 묶음 하나를 배정하는 것은 이번 화면 예시의 설계안이다. 실제 배정 규칙과 학과별 도전·핵심·여유의 수치 경계는 확정하지 않았다. 예시 분류에서 운영 임계값을 역산하지 않는다.

## 추천을 읽는 방식

| 학교 탐색 묶음 | 같은 학교에서 보이는 학과별 예시 |
| --- | --- |
| 도전학교 | 컴퓨터공학과는 도전, 응용수학과는 핵심, 환경학과는 여유 후보 |
| 핵심학교 | 경영학과는 도전, 경제학과는 핵심, 행정학과는 여유 후보 |
| 여유 후보 | 미디어학과는 도전, 사회학과는 핵심, 국어국문학과는 여유 후보 |

위 학교·학과·판정·수치는 모두 가상이다. ‘여기까지 지원 검토 가능’은 검토한 실제 모집행의 목록을 뜻한다. 학과를 한 줄로 서열화해 특정 학과 아래는 모두 가능하다고 판단하지 않는다. ‘여유’도 합격 보장이 아니다.

미확인 지원 자격, 개편으로 비교 불가한 입결, 미승인 예상 기준은 `확인 필요`로 분리한다. 이 개수는 추천 가능 학과 수에 포함하지 않는다. 확인 전 담기 버튼은 비활성화하는 화면안이다. 실제 지원 불가 행은 긍정 추천 대상에서 제외한다. 모집인원 미공개는 0명으로 표시하지 않는다.

## 3티어 구현 경계

1. **프레젠테이션:** 학교 카드와 학과별 결과를 표시한다. 부모 학교 분류를 학과에 복사하거나, 평균등급만으로 학과 지원 단계를 계산하지 않는다. 무료 사용자의 대학·학과 추천은 서버 응답부터 제한한다.
2. **애플리케이션:** 성적·결제 권한·본인 리포트를 확인한 뒤 각 실제 모집행에 공식 환산식을 적용한다. 같은 모집행의 비교 가능한 과거 입결 및 승인된 올해 예상 기준을 가져와 추천 단계와 이유를 생성한다. 비공개 원천표·가중치·운영 키를 브라우저에 전달하지 않는다.
3. **데이터:** 기존 검수 매핑 PK를 재사용한다. 대학·캠퍼스·학과명만으로 새로운 운영 식별자를 만들지 않는다. 환산 규칙, 누적 분포, 과거 지표 정의, 연도 간 척도 연결, 기본 예측·이슈 조정·채택값, 판정 버전과 기준일을 보존한다.

핵심 지원 학교는 `사용자 리포트 × 학년도 × 실제 모집행 PK`로 저장한다. 같은 학과가 기본 목록과 와일드카드에 동시에 나타나도 선택은 한 건이며, 2번 리포트 화면도 이 목록을 사용해야 한다. 실시간 추천·선택 집계의 단위 역시 대학 전체로 합치지 않고 실제 모집행을 기준으로 한다. 접기·탭 전환은 추천/선택 이벤트로 간주하지 않는다.

기존 전체 누적 기반 `school_screening.py`는 1차 탐색용으로 유지한다. 학과별 상세 판정을 그 모듈의 학교 범위 분류와 동일시하지 않는다. 과목 강점으로 유리해지는 후보와 와일드카드가 1차 탐색만으로 누락되지 않도록 상세 후보 확장은 별도 엔진에서 처리한다.

## 현재 결과와 다음 데이터 연결

- [작동하는 화면](preview/index.html): 대학 펼침, 학과 필터, 세 학교 묶음 전환, 모집단위별 담기, 와일드카드 선택 동기화, 무료 화면 제한 예시.
- [가상 응답 자료](handoff/candidate.mock.json): 대학 5개, 모집단위 14개. 기본 학교 3개에 각 4개 학과가 있으며, 와일드카드 3개 중 간호학과 1개는 기본 목록과 같은 ID다.
- [서버 연동 계약](handoff/candidate-contract.json): v0.7을 이어받아 학교/학과 분류 분리와 개별 환산, 판정 보류, 선택 중복 방지, 유료 제한을 추가했다.
- [검증 코드](verify.cjs): 실제 데이터 구조와 화면 상태 전환을 확인한다. [검증 기록](verification.json)에 9개 검사 통과와 브라우저 연결 제한을 기록했다. 로컬 HTTP 응답 200 및 저장 HTML 일치도 확인했다.

독립 HTML이므로 바로 열거나 이 폴더의 `preview`만 로컬 정적 서버로 제공할 수 있다. 원본 데이터 폴더 전체를 정적 서버로 공개하지 않는다. 예시의 유료/무료 전환은 표시 검토 기능이며 실제 인증·결제 보안이 아니다. 선택은 메모리에만 유지된다. 기존 2번 리포트 화면이나 운영 DB에 저장되지는 않는다.

실제 연동에는 검수된 대학별 공식 환산식, 승인된 자체 누적곡선과 비교 척도, 모집단위별 입결, 사용자와 함께 채택한 올해 예상 기준, 추천 단계의 판정 정책이 필요하다. 이러한 데이터가 확인되지 않으면 구체적인 지원 가능 학과를 확정해서 표시하지 않는다.
