# 구현 준비·검증 계획 v0.1

작성일: 2026-09-23 · 상태: 예시 파일 검토 전 준비안

## 확정된 구현 방향

- 주 사용자: 교사·입시상담자.
- 첫 화면: 개인 성적 입력 없이 대학의 정시 성적자료 정리본을 확인.
- 후속 핵심 흐름: 실제 수능 성적 입력 → 대학별 환산 → 지원 후보 비교 → 계산 근거 확인.
- 예시 파일을 화면 구성과 데이터 항목을 구체화하는 기준으로 사용.
- 첫 적용 학년도·대학 범위·공개 일정·계정·저장 방식은 아직 미정.

현재 요청은 시스템 기획과 구현 준비다. 예시 파일 확인 전에는 화면의 성적 지표, 입시결과의 뜻, 수식, 서비스 대상 범위를 확정하지 않는다.

## 다음 작업: 예시 파일을 실제 명세로 바꾸기

| 순서 | 확인·작성할 내용 | 산출물 |
|---|---|---|
| 1 | 파일별 역할: 원본 데이터, 기존 정리본, 화면 참고, 계산 예시 | 예시 파일 목록과 역할표 |
| 2 | 시트·표·열·행 구조, 표 머리글·주석·색·묶음의 의미 | 구조 설명과 항목 사전 |
| 3 | 정시 성적자료의 지표·대상 학년도·대상 집단·점수 기준 | 성적 지표 정의표 |
| 4 | 대학·캠퍼스·모집단위·전형·군·연도 키와 기존 자료의 대응 | 예시 ↔ 기존 33개 필드·추가 필드 매핑 |
| 5 | 첫 화면에서 그대로 보여 줄 항목과 펼쳐 볼 상세 정보 | 첫 화면 배치안과 탐색 흐름 |
| 6 | 수능 입력값·대학별 환산·상담 비교의 구체 예시 | 한 사례의 입력→계산→비교 명세 |
| 7 | 원문 근거·계산 규칙·검수 필요 항목 | 자료 보충·검수 목록 |

예시의 구성은 사용자 의도를 이해하는 기준으로 삼는다. 예시의 숫자나 계산식을 공식 입시 데이터로 사용할 때는 적용 학년도와 출처를 별도로 대조한다. 파일에서 의미를 확인하지 못한 항목은 사용자에게 물을 질문으로 남긴다.

기획용으로 제공된 학생 실명·식별정보는 화면의 필수 입력 요구사항으로 확대하지 않는다. 검토 문서에는 필요한 구조만 기록한다.

## 구현 순서와 완료 조건

| 단계 | 구현·준비할 것 | 완료 판단 | 주요 선행 조건 |
|---|---|---|---|
| M0 예시 기반 구체화 | 첫 화면, 지표 정의, 수능 입력·비교 흐름 | 예시 파일의 모든 주요 표·항목을 명세에서 설명 | 예시 파일 |
| M1 데이터 계약 | 키·출처·점수 정의·결측·버전·상태 | 실제 예시를 손실 없이 표현하고 기존 모집행과 연결 가능 | M0 |
| M2 첫 화면 시제품 | 성적 입력 없는 정시 성적자료 조회·필터·상세 | 예시의 주요 정보를 찾고 같은 정의의 값만 비교 | M0·M1, 공개 가능한 표본 자료 |
| M3 환산 규칙 | 대상 모집행의 공식 규칙·환산표·정답 사례 | 같은 수능 입력을 독립 계산과 대조해 일치 | 대상 학년도·학교·전형 결정 |
| M4 상담 흐름 | 실제 수능 입력·일괄 환산·후보 비교·계산 근거 | 실제 수능 한 사례를 처음부터 끝까지 처리 | M2·M3 |
| M5 검수·공개 운영 | 학교별 검수, 배포본, 권한, 오류 처리 | 승인 범위만 노출되고 이전 결과 재현·복귀 가능 | 운영 형태 결정 |
| M6 범위 확대 | 추가 대학·전형·저장·출력 등 | 같은 품질 기준으로 확장 | 시범 사용 결과 |

M2와 M3의 준비는 병행할 수 있다. 첫 화면을 구현하려면 모집표뿐 아니라 사용자가 뜻하는 ‘정시 성적자료’ 자체의 값과 정의가 필요하다. 현재 확인한 모집행 데이터만으로 성적결과 정리본이 준비되었다고 보지 않는다.

개발 일정은 예시 파일의 구조, 대상 규칙의 수·복잡도, 검수 인원, 공개 범위가 정해진 뒤 산정한다. 현재 문서에는 근거 없는 출시 날짜나 예산을 넣지 않는다.

## 시범 대상 선정 제안

첫 계산 시제품은 규칙이 서로 다른 3~5개 대학 묶음으로 검증하는 방안을 제안한다. 대학명·학년도·전형은 예시 파일과 사용자 범위를 확인한 뒤 결정한다.

표본은 실제 공식 요강을 읽고 다음 차이를 포함하도록 고른다: 표준점수/백분위 반영, 영어·한국사 등급 처리, 탐구 반영 수·대학 환산표, 과목 가산, 영역 선택, 단계별 반올림. 이것은 표본 선정 기준이며 특정 대학이 어떤 방식을 쓴다는 확정 데이터가 아니다.

각 학교에서 4개년 모집행·관계를 연속 검토하고 확인 범위를 기록한다. 계산은 서비스 대상 학년도의 규칙을 별도로 검증한다. 과거 모집인원이나 결과 지표가 미확인인 항목은 그 상태를 표시하며, 현재 학년도 계산 완료를 과거 자료 전체의 검수 완료로 확대하지 않는다.

실제 서비스 구현 시 데이터 구조 검사, 규칙별 계산 검사, 핵심 화면 통합 검사와 시범 상담으로 나누어 검증한다. 현재는 기획 문서의 경로·상호 일관성·기존 33개 항목 매핑을 확인하는 단계이며 위 기능 검사를 실행했다고 기록하지 않는다.

## 개발 환경 준비안

기술을 선택한 뒤 아래처럼 기존 데이터와 새 앱을 구분하는 구조를 제안한다. 아직 폴더·프로젝트를 생성한 상태는 아니다.

```text
Resource/                         기존 원본·메타·데이터 버전 보존
scripts/                          기존 수집·검수 코드 보존
docs/planning/                    이번 기획과 후속 결정 기록
app/                              새 사용자 화면 후보
service/                          API·환산·조회 모듈 후보
contracts/                        입력·응답·데이터 사전 후보
fixtures/                         공식 근거 또는 합성임을 명시한 검증 사례
releases/                         불변 배포 manifest 후보
validation_outputs/<run_id>/      실행별 새 검증 결과 후보
```

운영 DB·비밀 설정·실제 개인 성적 저장 위치는 배포 방식을 정한 뒤 결정한다. 원본 파일과 프로젝트 작업폴더를 운영 DB 공유 폴더로 그대로 사용하는 방식은 채택하지 않는다.

패키지 설치·빌드·DB 초기화 전에는 파일 삭제 부작용을 확인한다. 삭제가 필요한 명령은 대상·이유·영향을 제시하고 사용자 규정 범위를 받는다. 신규 출력은 실행별 경로에 생성하며 기존 출력이 있으면 덮어쓰지 않고 중단하거나 새 버전을 만든다.

## 착수·공개 준비 확인

화면 명세 착수에는 예시 파일과 그 역할 설명이 필요하다. 계산 엔진 착수에는 적용 학년도·대상 모집행·공식 성적 규칙·환산표·검증 사례가 필요하다. 공개 전에는 제공 범위, 항목별 근거, 계산 품질, 권한·저장 정책, 운영 담당과 변경 대응 절차가 정해져야 한다.

다음 대화의 첫 작업은 예시 파일을 열어 **첫 화면에서 무엇을 어떻게 보여 줄지**를 구체화하는 것이다. 그 결과에 맞춰 이 초안의 화면·데이터 사전·구현 과제를 수정한다.
