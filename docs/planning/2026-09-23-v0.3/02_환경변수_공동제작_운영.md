# .env와 공동 제작 운영 기준 v0.3

작성일: 2026-09-23 · [3티어 설계](00_3티어_보안_설계.md)

## 1. .env의 역할

.env는 실행 설정을 코드와 분리해 공급하는 파일이다. 보통 평문이며 암호화, 로그인, 방화벽, 권한 관리 또는 반출 방지 기능을 제공하지 않는다. .env를 읽은 사람은 그 안의 값을 복사할 수 있다.

비밀값으로 접속하는 DB·API·저장소 자체가 권한을 검사해야 한다. 파일 이름이 .env라는 이유로 웹 서버가 자동으로 보호한다고 가정하지 않는다.

| 분류 | 예 | 보관·공유 |
|---|---|---|
| 공개 화면 설정 | API의 공개 경로, 앱 표시명, 개발용 mock 선택 | .env.frontend.example에 공유 가능. 브라우저에서 보여도 되는 값만 포함 |
| 개발 서버 설정·비밀값 | 개발 DB 접속값, 세션 서명 비밀, 내부 저장소 위치 | 팀 비밀값 관리 공간에서 전달하거나 개인별로 발급. 실제 값은 저장소에 커밋하지 않음 |
| 운영 서버 비밀값 | 운영 DB 자격, 세션/서비스 서명 키 | 호스팅 환경의 비밀 저장 기능에서 실행 시 주입. 복제된 평문 파일 수를 줄이고 접근·변경 기록 |
| 원본·모델·누적 데이터 | Excel·DB·배포표·모델 자산 | .env에 넣지 않음. 비공개 데이터 저장소에서 파일·레코드로 관리 |

사용자 결정에 따라 공동 제작자 전원에게 전체 코드·데이터 접근을 허용한다. 공유 계정 하나를 돌려쓰기보다 같은 권한의 개인 계정을 발급하면 누가 사용했는지 추적하고 특정 계정만 중지할 수 있다. 사람의 전체 열람 범위와 배포·삭제 같은 변경 권한은 별도 정의한다. 특히 이 프로젝트는 명시적 허용 전 어떤 파일도 삭제하지 않는다.

## 2. 프레임워크와 브라우저 노출

Next.js의 NEXT_PUBLIC_*와 Vite의 VITE_* 환경변수는 브라우저용 코드에 포함될 수 있다. 해당 이름으로 DB 비밀번호·서버 키를 두지 않는다. 접두어가 없는 서버 값도 API 응답이나 HTML·클라이언트 props로 직접 전달하면 노출된다.

예시 파일의 PUBLIC_*는 현재 설계상 공개 설정을 나타내는 이름일 뿐이다. 특정 프레임워크가 자동으로 읽는다고 보장하지 않는다. 스택 선정 후 Next.js 또는 Vite 등 실제 도구에 맞게 공개 설정만 명시적으로 연결한다.

프론트엔드 빌드에 모든 process.env 또는 서버 설정 객체를 통째로 넘기지 않는다. 공유 contracts 패키지에 비밀 설정을 읽는 모듈을 포함하지 않는다.

근거: [Next.js 환경변수](https://nextjs.org/docs/app/guides/environment-variables), [Vite 환경변수](https://vite.dev/guide/env-and-mode).

## 3. 팀 공유 방식 제안

1. 코드 저장소에 키의 이름·필수 여부·뜻만 적은 .env.example을 둔다.
2. 실제 개발 접속값은 접근 기록이 남는 팀 비밀 저장 공간이나 암호화된 공유 수단을 이용한다.
3. 가능하면 개인별 DB·개발 API 계정을 사용한다. 팀원에게 같은 접근 범위를 주면서도 계정은 구분할 수 있다.
4. 개발·검증·운영의 자격과 데이터 연결 대상을 분리한다. 실제 운영값을 mock 테스트나 프론트엔드 빌드에 주입하지 않는다.
5. 운영의 공용 서명 키처럼 서비스가 공유해야 하는 값은 서버 실행 환경에서 관리하고, 유출·퇴사·역할 변경 때 회수·교체할 절차를 둔다.
6. 중요한 비밀값 누락·빈 값·예시 문자열은 서버 시작 시 거절한다. 코드에 개발용 기본 비밀을 넣어 운영까지 동작시키지 않는다.

전체 접근을 가진 공동 제작자가 자료를 가져가는 행위 자체는 이 구조만으로 차단할 수 없다. 여기서는 신뢰 팀의 협업을 유지하면서 우발적 공개와 외부 접근을 줄이고 기록하는 것을 목표로 한다.

OWASP는 중앙 관리·세분화된 권한·접근 기록·비밀값 교체와 수명주기 관리를 권고한다. [Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## 4. 현재 작업 공간에 적용할 때

현재 경로는 G:\내 드라이브\Jungsi_touch이다. 실제 동기화·공유 설정은 확인하거나 변경하지 않았다. 공유 대상과 백업 범위를 확인한 뒤 실제 비밀 파일의 저장 위치를 정한다.

.gitignore는 Git의 새 추적을 제어할 뿐, 동기화 서비스의 업로드·폴더 공유·이미 추적된 이력을 보호하지 않는다. 따라서 실제 비밀 파일은 필요한 공유 범위가 확인된 경로 또는 비밀 저장 기능으로 관리하는 안을 제안한다.

제공된 .env.*.example에는 실제 자격증명이 없다. 현재 애플리케이션이 자동으로 로드하도록 설정한 파일도 아니다. 이번에 실제 .env를 만들거나 기존 원본·데이터·비밀 파일을 이동하지 않는다.

비밀이 실수로 저장소 이력이나 배포물에 들어갔다면 무효화·교체를 먼저 검토한다. 파일·이력 삭제가 필요할 경우에는 프로젝트의 삭제 금지 규칙에 따라 대상을 명시하고 사용자의 허용을 받아야 한다. 이번 설계가 그 삭제 권한을 부여하지 않는다.

## 5. 배포·API·데이터의 실제 통제

| 항목 | 설계 기준 |
|---|---|
| 배포 산출물 | 웹 파일만 허용 목록으로 선택. 원본, DB 덤프, 환경변수, 엔진 자료 제외 |
| 데이터 네트워크 | 운영 DB·저장소 공개 접속 차단. API와 내부 작업의 전용 자격 사용 |
| API 권한 | 요청별 권한·객체 접근 검사. UI 역할값과 CORS만으로 판단하지 않음 |
| 세션 | 서버 발급 세션을 쓸 경우 Secure·HttpOnly·적절한 SameSite 및 CSRF 대응. 제공자·세션 방식은 구현 때 결정 |
| 개인 결과 | 개인 응답은 공유 캐시에서 제외. 익명/회원 여부와 별개로 세션 간 혼합 방지 |
| 로그·관측 | 비밀값·개인 성적 본문·전체 모델 자료를 기록하지 않음. 추적 ID·작업·주체·배포 버전·처리 결과 중심 |
| 자동화 남용 | 요청·응답 크기와 비용 제한, 반복 입력 스캔 감지, 서버 측 정책 집행 |
| 내부 관리 | 전원 접근 정책을 개인 계정으로 구현. API 서비스 계정과 사람 계정을 구분 |
| 원본 보존 | 기존 자료·버전 유지. 정리·회수 과정도 삭제 규칙을 준수 |

## 6. 구현·검증 작업 순서

1. 전원 접근 가능한 비공개 코드·자료 공유 범위와 개인 계정 체계를 정한다.
2. 계약과 가상 응답으로 프레젠테이션을 구현한다.
3. 서버 전용 환산·누적 엔진을 연결한다.
4. 공개·개인·내부 관리의 API 응답과 접근 정책을 구현한다.
5. 개발 환경 설정을 개인별로 연결하고 운영 비밀 주입 방식을 설정한다.
6. 번들·응답·정적 파일·로그·백업 노출, 접근권한 우회, 반복 조회 제한을 실제 배포 환경에서 확인한다.

이 문서와 예시의 정합성 확인은 운영 시스템의 보안 검증을 대신하지 않는다.
