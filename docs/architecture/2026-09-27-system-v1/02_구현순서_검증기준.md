이번 작업은 설계 문서와 가상 계약 예제를 추가한 것이다. 운영 환산 엔진·실제 대학 규칙·자체 곡선·입결 수집·API·회원 결제·Kafka를 구현 완료했다고 표시하지 않는다. 기존 코드의 테스트 수나 과거 통과 기록을 이번 문서 검증 결과로 다시 세지 않는다.

이는 의존 순서다. 화면의 가상 API 연동과 회원·조회 구현은 규칙 수집과 함께 진행할 수 있다. 그러나 특정 학교의 4개년 모집표 검수는 한 묶음을 끝낸 뒤 다음 학교로 넘어간다. 연도별 전국 순회나 구조 검사만으로 완료 표시하지 않는다.

1페이지는 개인 분석보다 먼저 사용할 수 있게 만들 수 있다. 자체 누적이 아직 없으면 검증된 원 입결과 ‘자체 누적 준비 중’을 표시하고 가상 누적을 운영값으로 채우지 않는다. 마찬가지로 대학 환산이 준비됐더라도 비교 분포·컷이 준비되지 않았으면 해당 숫자와 비교 보류를 구분한다.

## 3. 환산 엔진의 첫 검증 범위

처음부터 모든 대학의 예외를 추측해 넣기보다, 실제 공식 자료가 준비된 소수 대학에서 서로 다른 공식 유형을 검증한다. 대학명과 개수는 미정이다.

검증해야 하는 유형 후보:

- 표준점수·영역별 반영비율·영어 등급 조정.
- 탐구 변환표준점수 및 선택과목 가산.
- 백분위 사용, 일부 영역/탐구 상위 과목 선택.
- 여러 계산식 중 유리한 산식 선택.
- 수능 부분점수와 면접·학생부 등 다른 요소가 함께 있는 전형.

각 유형은 실제 대학 공식 근거가 확보된 경우에만 구현한다. 같은 학교의 여러 모집행이 하나의 규칙을 공유하는지, 예외가 있는지 확인한다. 샘플 대학 검증을 전국 대학 엔진 완료로 표현하지 않는다.

## 4. 데이터 처리 작업의 경계

```text
원문 보존
  → 출처·원문 범위 기록
  → 모집표/규칙/입결 추출 초안
  → 학교 4개년 검수 및 기존 PK 연결
  → 정규화된 별도 버전 생성
  → 산식/분포/예측 검증
  → 공개 가능한 범위 선택
  → 서비스 공개 버전 발행
  → 개인 재계산·순위 인덱스 갱신
```

수집·모형 보정·대량 대학 재계산은 작업자에서 수행한다. 개인의 단순 환산과 승인된 곡선 조회는 API에서 빠르게 처리할 수 있다. 요청마다 원본 엑셀을 열고 수만 행을 탐색하는 구조는 피한다.

- 입력 자료는 원문 보존층, 정규화 자료, 공개용 검증 자료로 나눠 버전을 남긴다.
- 현재 엑셀은 출처/검수 자산으로 보존하고, 운영 조회는 검증된 데이터를 적재한 DB를 기준으로 한다.
- 규칙 재사용으로 같은 성적·같은 규칙·같은 변환표는 한 번 계산해 여러 모집행에서 재사용한다.
- 계산 캐시는 입력 전체의 식별자/버전과 규칙·표·출력 계약 버전을 포함한다. 선택과목·영어·한국사를 빼고 국수탐 총점만으로 캐시하지 않는다.
- 총점 누적 캐시와 대학 환산 캐시는 다르다. 같은 총점의 학생들이 같은 대학 환산값을 공유하지 않는다.
- 전체 곡선 재생성과 모집인원 변경만으로 생기는 재추천은 영향 범위가 다르다. 변경의 의존 관계에 따라 필요한 결과를 다시 만든다.

## 5. 코드 배치 제안

기존 파일을 이동·삭제하지 않고 다음 구조를 확장하는 안이다. 아래 경로가 이미 구현됐다는 뜻은 아니다.

```text
apps/web/                       화면·입력·리포트·운영자 UI
services/api/                   인증·이용권·서비스 계층·API
services/workers/               수집·곡선 제작·대량 재계산·이벤트 처리
src/jungsi_touch/
  percentile.py                 기존 총점 누적 계산
  joint_distribution.py         기존 조합별 인원 집계
  scoring/                      제안: 공식 규칙 계약·연산기·조회표·추적
  curves/                       제안: 전체/대학 분포 계약·제작·검증
  forecasts/                    제안: 입결 연결·기본 예측·이슈 조정
  recommendations/              제안: 후보·유불리·학과 도달 판정
packages/contracts/             공개 API 타입/명세, 핵심 데이터 없음
data_contracts/                 제안: 내부 규칙·표·공개 버전 계약
scripts/                        기존 도구 보존, 배치 진입점
Resource/                       기존 원문 보존
outputs/                        이전 결과 보존, 새 산출 버전 추가
```

규칙 패키지는 DB 또는 비공개 파일 저장소에 버전별로 저장한다. 코드 리뷰가 필요한 규칙 초안은 내부 저장소에서 함께 검토할 수 있으나 프런트엔드 번들에 포함하지 않는다. 실제 비밀값을 포함한 .env를 배포 이미지/공개 정적 파일에 넣지 않는다.

## 6. 운영 공개 전 인수 시나리오

1. 무료 사용자가 성적 없이 대학·학과를 검색해 네 연도 결과를 보고 합격권과 상위70%를 각각 식별한다. 미공개 인원이 0으로 나오지 않는다.
2. 실제 수능 성적을 입력한 무료 사용자는 전체 누적을 볼 수 있고, API 직접 호출로 유료 대학 분석을 얻지 못한다.
3. 총점이 같고 국어·수학 구성만 다른 두 학생의 전체 누적은 같으며, 대학 공식 반영식이 다르면 환산점수와 유불리는 달라질 수 있다.
4. 학부모가 동일 대학의 서로 다른 학과를 검토할 때, 같은 환산점수라도 과거 기준·올해 예상 컷이 다르게 표시된다.
5. 수학/탐구 강점이 유리한 후보가 좁은 전체 누적 필터 때문에 사라지지 않는다. 와일드카드의 지원 조건 미충족은 추천에서 제외한다.
6. 대학 변환표가 미공개이면 작년 표를 가져오지 않는다. 수능 외 요소가 없으면 수능 부분점수만 표시하고 전형 총점·최종 합격을 확정하지 않는다.
7. 예측 운영자가 학교 이슈를 반영하면 기본 예상 컷, 조정 근거, 채택값과 적용 모집행을 추적할 수 있다.
8. 핵심 지원 학교 선택/해제, 성적 수정, 같은 이벤트 재전송, 오래된 이벤트 역순 도착 이후에도 두 집단의 현재 인원·순위가 기준 DB와 일치한다.
9. 같은 점수의 학생은 공동 순위가 같다. 전체 관심 인원과 유효 점수 보유 인원이 다른 경우 분모가 각각 표시된다.
10. 자료 공개 버전 변경 시 옛 점수와 새 점수가 같은 순위에 섞이지 않는다. 이전 리포트는 당시 버전으로 재현된다.
11. 클라이언트 번들·네트워크 응답에서 전체 곡선·핵심 원본·다른 학생 정보·운영 비밀값이 전달되지 않는다.
12. 표 구조/PK 검사와 원문 모집표 전수 검수를 별개의 항목으로 보고한다.

## 7. 아직 확정하지 않은 선택

- 최초 운영 학년도, 대학 범위, 정확한 과거 입결 네 연도, 출시 시점. 2027 정보 표시는 기존 화면 요구로 유지한다.
- Next.js/FastAPI/PostgreSQL 등 기술 채택과 배포 환경, 초기 트래픽·운영 비용 한도.
- 이용권 가격·기간, 비회원 조회 범위, 실시간 인원/순위의 무료 공개 범위.
- 자체 분포의 최종 보정 모형·비교 모집단·정확도 기준·승인 절차.
- 추천 후보 구간, 표시 순서·불확실성 표현, ‘상향/적정/안정’ 등급의 실제 검증 기준.
- 학교별 공식 산식/변환표 공개 일정, 원문 근거가 부족한 규칙의 처리 범위.
- 학생·학부모·상담자 계정과 실제 학생의 연결·중복 방지 방법.
- Kafka 운영 방식과 실시간 목표. 설계상 p95 5초는 측정 전 목표이며 보장치가 아니다.

위 미정 사항 때문에 산식 계약·자료 검수 구조·화면 API를 설계하는 작업을 멈출 필요는 없다. 운영값·사업 약속·추정 정확도를 확정하는 시점에는 각각의 근거와 결정을 남긴다.

## 8. 이 설계에서의 우선순위

가장 먼저 확보할 연결은 **실제 모집행 PK → 공식 규칙 버전 → 공식 변환표 → 학생별 계산 결과·근거**다. 여기에 승인된 자체 분포와 입결 비교를 연결해야 서비스의 차별점인 ‘나에게 유리한 대학과 실제 검토 가능한 학과’가 나온다. Kafka는 그 뒤에 만들어지는 현재 추천·선택 상태를 신뢰성 있게 전달하는 역할을 맡는다.
