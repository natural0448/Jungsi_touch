# 현재 개발현황과 기획·라우팅 문서 동기화

이 문서는 공통 명세 service_spec.json에서 생성한다. 현재 버전은 1.9.120이며 기획·라우팅·계층 문서를 같은 변경으로 갱신한다.

## 모든 에이전트의 필수 동기화 순서

1. 브랜치·HEAD·최신 정확 SHA의 CI/검산 영수증과 공통 명세/현황/코드 색인을 읽고 이번 작업의 기준 커밋을 고정한다.
2. 고정 SHA부터 Git 변경 목록과 함수/클래스 시그니처 차이를 기계적으로 추출한다. 해당 코드와 연결된 요구사항·API·계층·짝 문서를 먼저 검토한다.
3. 이미 검증한 코드와 자료는 버전·해시·적용 범위를 확인해 재사용한다. 미병합 PR·스테이징·담당자 보고를 develop의 확정 구현과 구분한다.
4. 다른 PC 재개 시 현재 코드 SHA와 최신 비공개 단일 정본/인계 포인터를 따로 고정한다. 마지막 합격 예비번호는 최종 합격 예비번호·번으로 표시하고 인원과 치환하지 않는다. 같은 수집값/관측은 한 번 저장하며 검수는 PK/관측ID·항목·O/X·근거 참조로 분리한다. 단일 DB writer가 현재 실제 지문/중복을 확인하고 포인터를 마지막에 갱신한다.
5. 업무 변경은 요구사항 ID·화면/API·권한/소유권·계층·검증과 운영 미완료 상태를 정본에 반영하고 --sync로 기획·라우팅·3티어·브랜치·현황 문서를 함께 생성한다.
6. 이번 파일만 stage하고 --staged --base로 변경 범위를 확인한다. 코드/공유 도구/테스트와 정본·기획·라우팅·3티어·브랜치·현황 문서를 같은 커밋에 포함한다.
7. 기존 동일 스냅샷 문서/코드/계층/비공개/브랜치 검사, 정상 커밋·푸시 훅과 정확 SHA의 CI를 모두 통과시킨다. 전체 자동 정합성 검사는 계속 실행한다.
8. 완료/인계에 기준·최종 SHA·변경 파일 수·재사용 범위·동기화 문서·검증과 NOT_RUN을 기록한다. 다음 에이전트는 이 검증 커밋 이후부터 확인한다.
9. 실제 인증/운영 이식은 supabase_deployment_contract.live_execution의 단계와 기존22 operation별 코드·native·배포 상태를 함께 갱신한다. PASS는 등록 Edge 파일/SHA·정확 후보 커밋·비공개 영수증 SHA/범위가 있을 때만 기록하며 계정·토큰·실제 자료는 공개 문서에 넣지 않는다.
10. 현행 상태표는 live_execution 원장의 코드·실 연결·배포와 단계에서 자동 생성한다. latest_verified_source에는 이미 검증한 정확 SHA·CI·소스 검산 범위만 기록하고 이전 development_state를 현재 상태로 복사하지 않는다.
11. 이 재개점의 정확 소스·승인 목적·영수증 범위와 해시부터 재사용한다. 005·불변 발행·성공한 격리 검수 namespace를 다시 실행하지 않는다. 함수 설치/생존·Storage·SQL 검수를 22업무의 native/deployment 완료로 세지 않는다. 새 설정 등록은 기존 소유자/관리자가 수행하고 정상 목록 digest와 같은 배포의 준비 상태로 대조한다. 등록 완료 회신만으로 PASS로 바꾸거나 설정 권한을 우회하지 않는다. 단계가 바뀌면 정본·기획·라우팅·운영 문서를 같은 커밋에서 갱신하며 매 작업 전체 scan을 반복하지 않는다.
12. API 연결 전 선행 작업은 live_execution.preconnection_preparation의4개 패키지·기존22 operation별 인수 조건을 따른다. 수집된 요강과 실행 규칙·시험별 추정곡선·현재 catalog를 분리하고 기존 검산을 재사용한다. 준비된 case는 실 JWT/OTP/BFF·운영 인수 증거가 아니며 실제 실행 상태는 live_execution.operations 원장에만 기록한다.

## 명령과 검사 범위

```text
python -B scripts/audit_documentation_sync.py --sync
python -B scripts/audit_documentation_sync.py --base <verified-commit>
# 검토한 파일만 명시해 stage한 뒤 동일 index를 검사
python -B scripts/audit_documentation_sync.py --staged --base <verified-commit>
python -B scripts/check_project_consistency.py --staged
```

--sync는 해시가 바뀐 코드의 AST를 갱신하고 이전 명세·문서를 outputs에 보존한다. 변경이 없는 코드의 시그니처는 재사용한다. --base는 한 번 고정한 커밋과 변경 소스·색인·짝 문서를 대조한다. 코드 본문만 바뀌어도 해시를 갱신하며 새 파일·삭제·파싱 실패·문서 변조를 통과시키지 않는다. 기존 커밋에 색인이 없으면 최초 색인 검증을 한 번 수행한다. 이후 색인이 있는 검증 커밋을 기준으로 변경 범위를 좁힌다.

필수 훅·CI는 같은 Git 스냅샷 전체의 비공개 파일·계층·권한·생성 문서·시그니처 정합성을 독립 검사한다. 이 자동 검사는 계속 실행한다. 에이전트가 전체 코드를 다시 읽거나 이미 검수한 원자료를 재수집하는 작업은 기본 절차가 아니다.

## 범위를 넓히는 조건

- 검증 커밋/색인이 없거나 무효면 최초 공개 코드 색인을 검증하고 기준을 새로 고정한다.
- 새 코드 경로·언어/파서·문서 스키마가 들어오면 그 경로/파서의 색인 및 검증 범위를 추가한다.
- 해시·시그니처·문서·요구사항/구현 참조가 어긋나면 해당 파일과 의존/짝 문서만 추가 확인한다.
- 원자료 개정/불일치 또는 사용자의 명시적 전수 검수 요청이 있으면 기존 근거를 재사용하고 해당 학교 4개년/요청 범위를 확인한다.

넓힌 사유·파일 범위·재사용 근거를 검사 영수증에 기록한다. 원문 모집표 전수 검수, 코드 정합성, 운영 발행·브라우저 인수는 서로 다른 검증이다.
